What this is

OpenMCPGateway sits in front of one or more MCP servers. Clients point at https://<host>/g/<slug>/mcp; the gateway authenticates the caller, applies its gate and a per-minute budget, forwards the request to the real server over the private network, and records what happened.

The upstream does not need to be reachable from the internet, and it does not need to know who the caller is: the gateway terminates identity and forwards its own credential when the upstream demands one (upstream_token).

The panel answers the same questions in the same shape: the Traffic screen carries totals with the change against the previous window, a volume chart, and breakdowns by outcome, gateway and caller — and a row in any table opens a drawer with the rest of that row instead of navigating away from the list.

LayerBehaviour
AuthenticationOAuth proxy per gateway (Google, GitHub, Microsoft, Discord, custom OIDC) or a bearer key hashed with SHA-256
AuthorisationMembers of the tenant that owns the gateway. A key issued here works too.
Rate limitPer subject, per gateway, counting JSON-RPC requests. Handshakes are free

Quickstart

You need a Postgres the gateway can reach and a hostname that terminates TLS in front of it.

# 1. run it
export OMG_DATABASE_URL=postgresql://omg:omg@127.0.0.1:5432/omg
export OMG_SESSION_SECRET=$(openssl rand -hex 32)
export OMG_BASE_URL=https://gateway.example.com
omg serve

# 2. create the first account, then a tenant, in the browser
open https://gateway.example.com

The first account creates a tenant and becomes its owner. Everyone else either joins with the tenant's join code or is added by an administrator.

The tenant arrives with a console gateway already pointing at this deployment's own read-only MCP. Point an agent at /g/console/mcp with the API key from its page and ask it what the deployment is doing — no upstream to configure.

Point a client at a gateway as soon as one exists:

// opencode.json
{
  "mcp": {
    "my-server": {
      "type": "remote",
      "url": "https://gateway.example.com/g/my-server/mcp"
    }
  }
}

Gateways

A gateway is a slug, an upstream URL, and a policy. The slug is global: /g/<slug>/mcp is the string people paste into clients, so two tenants cannot both own rancher.

One gateway is created for you: console, pointing at this deployment's own read-only MCP. The slug is global because /g/<slug>/mcp is a public URL, so on a deployment with several tenants the first one takes console and the others take console-<tenant id> — the id, not a counter, so the address still says whose gateway it is.

target_url is the streamable-HTTP endpoint of the upstream, including its path (http://rancher-mcp.support.svc.cluster.local:8000/mcp). It must be http:// or https://.

A gateway also decides which tools it exposes. The allowlist is a set of upstream tool names; empty means everything the upstream serves, which is how every gateway starts. It can be narrowed per credential source — the hosted identity provider (google, github, oidc), an extra verifier's label, or api_key — so one route gives a bot a smaller catalog than the person signed in beside it, without publishing two gateways to the same upstream. A source with no list of its own inherits the gateway's, and clearing a source's list puts it back to inheriting. A tool outside the list disappears from tools/list and a tools/call for it answers 403 naming the tool, so a client that kept an old name in its config gets a sentence instead of a silent success or a typo hunt. The gateway's page probes the upstream on demand: a real handshake, the tool count, and the reason it failed. A dead upstream used to look like a quiet, healthy gateway.

The panel reads the upstream catalog directly to fill that list - not through the gateway, which would answer with the filter it is already applying. A configured name the upstream no longer serves stays visible and marked, because dropping it silently on the next save would erase a decision the operator made.

Authentication modes

none - no authentication. Fine on a private network; the panel warns while any such gateway is enabled.

api_key - the caller sends Authorization: Bearer omg_.... The key is stored as a SHA-256 hash (that is what authentication compares) next to a sealed copy of the plaintext, encrypted with the deployment secret. The response that mints it returns the plaintext, and the gateway's page carries an eye icon for a key that has never been read: clicking it decrypts the sealed copy, shows the key once, and wipes it. After that the hash is all that remains, and the only way back to a readable key is rotating it. A key can be issued with an expiry. Past it the key no longer authenticates, and a rotation inherits the deadline of the key it replaces — the point of rotating is to change the secret, not to extend how long it is trusted.

The operator approves once, and that account is a member from then on.

The client does not need a token checked into a dotfile for OAuth mode - that is the point. For API-key mode it does, which is why the key is per gateway and revocable on its own.

A gateway can also have more than one way in. oauth mode accepts API keys on the same route when allow_api_key is set, and accepts tokens from additional issuers listed under verifiers - each with a label, issuer, optional audience and JWKS URL. The extra issuers have no login flow of their own: the client already holds a token from its provider, and the gateway only verifies the signature, the issuer and the audience. One URL, one gate, one rate limit, and no second gateway per credential type.

Who may call is not a list on the gateway. A caller is admitted when their account belongs to the tenant that owns it - the same rule the panel applies to editing one, so 'who may use this' has one answer instead of two that drift. Membership is read per request, so removing someone or disabling their account closes the gateway door on their next call. API keys are exempt because a key embeds its own id rather than naming an account: a key is admitted while its hash matches a live key here, and revoked by revoking the key.

# API-key call
curl -sS https://gateway.example.com/g/rancher/mcp \
  -H 'Authorization: Bearer omg_...' \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"0"}}}'

Members and roles

Everything is scoped to a tenant: gateways, members, roles, traffic, the audit log. An id from another tenant is a 404, not a 403 that confirms it exists.

Permissions are a closed catalog. A typo is refused with a 422 naming the field, because the alternative is a role that grants nothing and says nothing.

PermissionGrants
gateways:read / writeSee the gateway list, and change slugs, targets, auth and limits
keys:read / writeSee key ids, and issue, rotate or revoke them
traffic:readRead request stats and the recent-request log
audit:readRead the append-only event log
config:read / writeExport and apply the YAML file
members:read / writeSee the address book, and add people
roles:read / writeSee the role table, and define or edit roles

Two roles are built in and cannot be edited or deleted, because neither is a policy decision:

RoleIdPermissions
ownerrole_ownereverything
viewerrole_viewerevery read permission

A member added without a role lands on viewer: an omission narrows access, never widens it. Delegation may only narrow too - nobody can grant a permission they do not hold themselves, or members:write would be a path to role_owner. The same rule applies to the config file.

Permissions are resolved per request from the read models, so editing a role or reassigning someone takes effect on their next click. No re-login, no stale session.

Config as code

The panel and a YAML file are two front doors onto the same command handler. Neither is privileged: a gateway created in the browser exports to the file, and a file applied by CI lands in the same event log as a click.

gateways, roles and members are all declared in the file, so a tenant can be rebuilt from a commit. Secrets are never exported - write ${ENV_VAR} and the server resolves it from its own environment at apply time.

# gateways.yaml
gateways:
  - slug: rancher
    name: Rancher cluster
    target_url: http://rancher-mcp.support.svc.cluster.local:8000/mcp
    description: read the cluster, restart and scale
    auth:
      mode: oauth
      idp: google
      client_id: ${GOOGLE_CLIENT_ID}
      client_secret: ${GOOGLE_CLIENT_SECRET}
      upstream_token: ${RANCHER_MCP_TOKEN}
    rate_limit: 120
    allow: [someone@example.com]

roles:
  - name: Auditor
    permissions: [gateways:read, traffic:read, audit:read]

members:
  - email: auditor@example.com
    password: ${MEMBER_PASSWORD}
    roles: [Auditor]

prune: false

Merge semantics: the file is authoritative for what it declares. A gateway left out of the file survives, so a typo cannot delete production. prune: true opts into deletion - it applies to gateways only; members are never pruned by omission, because an account that disappears from a file is far more likely to be a merge accident than an intention.

Members reconcile by email: an existing member whose roles differ gets them replaced, and one whose roles match is left alone. password is only used when the account does not exist yet, so it appears in a reviewed file as ${MEMBER_PASSWORD} and never in an export - which is also why exporting and re-applying is a no-op. A new account with no password is refused, because inventing one would be a credential nobody can sign in with.

A role whose name matches a built-in (owner, viewer) may be named but not redefined: the file would otherwise narrow every existing member at once.

# round-trip from the shell
omg export --tenant tn_local > gateways.yaml
omg apply gateways.yaml --tenant tn_local

omg apply prints what changed and any errors, and exits non-zero when a declaration failed - which is what makes it usable in CI. Newly issued API keys are printed once, because that is the only time the plaintext exists.

The panel's Config as code page does the same thing: Validate parses and resolves placeholders without touching state, Apply runs the commands.

HTTP API

Everything the panel does is an endpoint under /api, authenticated by an HttpOnly session cookie. The MCP routes themselves live at /g/<slug>/mcp and speak JSON-RPC, not this API.

Every list is cursor-paginated: ?limit=50&before=<cursor>, answering {items, next}. next is null on the last page, and limit is clamped to 200 rather than refused.

Each list also accepts its own filter fields as query parameters, one box per column in the panel. Text columns match a fragment (?name=anch finds rancher), status and enabled match exactly, and every list carries an id box for the row you only half copied. An unknown field is a 422 naming the fields that exist — a filter silently ignored is worse than an error.

Ordering is ?sort=<column>&order=asc|desc. The sortable columns are a closed set per list: gateways by created_at, updated_at, name or slug; traffic by occurred_at, duration_ms, status or subject; the audit log by occurred_at, actor or type; members by email and created_at; roles by name and created_at. An unknown key is a 422 that lists the legal ones.

A cursor means after this row, in this order, so it is bound to the sort it was minted under. Change sort or order and start from the first page: reusing the old cursor is a 422, not a silently holed list.

Two endpoints do not fit the CRUD shape and are worth knowing: POST /api/gateways/<id>/keys/<key_id>/reveal answers the sealed plaintext once and 409 afterwards, and GET /api/gateways/<id>/upstream-tools asks the upstream what it serves so the allowlist can be ticked rather than typed. PUT /api/gateways/<id>/tools replaces the list, or one credential source's list when the body names a source. GET /api/requests.csv answers the same filters as /requests, as a file; POST /api/config/plan says what an apply would change without changing it, and POST /api/gateways/<id>/test probes the upstream with a real MCP handshake.

Four endpoints answer questions the CRUD shape cannot: GET /api/gateways/<id>/history is that gateway's own event stream, newest first, paged and filtered with the audit log's own vocabulary and with secret values redacted; POST /api/gateways/<id>/restore re-applies the configuration at a version and appends one gateway.restored fact — credentials and keys are not restored, because a revoked key must stay revoked; GET /api/events.csv is the audit log as a file with the same filters and the same tenant scope; and /api/gateways/<id>/webhooks registers a URL that receives every observation the guard records, signed with an HMAC-SHA256 of the body.

The console MCP

The gateway exposes a read-only MCP server of its own at /mcp, so an agent can answer questions about this deployment: which gateways exist, what failed in the last hour, what the audit log says about a role change.

It is read-only by construction - every tool is a query, none is a command - and it is tenant-scoped: a token minted by one tenant's operator can only ever read that tenant's rows.

Every new tenant already has one gateway pointing at it. It is created with the tenant, named console, with the deployment's own /mcp as its upstream and an API key for the caller — so the first thing a new tenant can do is plug an agent in without configuring anything. It is a gateway like any other: same auth, same rate limit, and its questions land in the traffic log next to every other call.

Tenants that existed before this feature get the same gateway on the next boot: the backfill asks for tenants with no gateway row pointing at /mcp, so an owner who deleted theirs keeps it deleted.

Connect to it exactly like a hand-made gateway:

// opencode.json
{
  "mcp": {
    "gateway-console": {
      "type": "remote",
      "url": "https://gateway.example.com/g/console/mcp",
      "headers": { "Authorization": "Bearer omgc_gateway_api_key" }
    }
  }
}

The key is issued when the tenant is created and shown once, on the gateway's page. Rotate it there if it leaks; delete the gateway if you would rather call /mcp directly.

1. Mint a token: POST /api/mcp/token with your session cookie. The plaintext is returned once, exactly like an API key.

// opencode.json

Operating it

Logs are one JSON object per line on stdout, built for Loki / Grafana. Useful fields to build dashboards on: event, gateway, subject, outcome, status, duration_ms. Set the level with OMG_LOG_LEVEL.

{"ts":"2026-11-02T11:04:14.538Z","level":"info","logger":"gateway","msg":"proxy.request","event":"proxy.request","gateway":"rancher","subject":"api-key:key_ab12","outcome":"allowed","status":200,"duration_ms":18,"ip":"203.0.113.7"}

Rate limiting is a sliding window per (gateway, caller). With OMG_REDIS_URL set, the counters live in Redis and every replica shares them, so replicas: 2 means the configured limit and not twice it. Without it the limiter is in-process: correct for a single replica, N times the limit at N. A Redis that is down fails open and logs - one lost window of accounting beats an outage.

OAuth proxy state (client registrations, upstream tokens, jti mappings) lives in the same Postgres, encrypted at rest, so a rollout does not log every connected client out. That part is already replica-safe, and with OMG_REDIS_URL set the limiter is too.

State is event-sourced. Every change is an append-only event and the read models are projections of it, which is what makes the audit log trustworthy and lets two replicas share one database without a cache-coherence story.

The schema is versioned in code (infrastructure/db/migrations.py): a numbered list of steps, recorded in schema_migrations. Boot applies whatever this build has not applied yet, so an upgrade is a rollout, not a manual psql session. The read models live in their own schema, readmodels — every table prefixed rm_ — while events, the uniqueness tables and the history stay in public. That split is the point: a projection is rebuildable from the log, so DROP SCHEMA readmodels CASCADE followed by a boot is a safe reset that the next boot notices and repairs. Nothing the log depends on is in there. OMG_RETENTION_DAYS prunes the request log at boot. Past the cutoff, request.observed events, rm_requests_tail and rm_request_stats are deleted; audit events never are, because the log of who changed what is not the log of who called. 0, the default, keeps everything.

GET /metrics serves Prometheus's text format: omg_proxy_requests_total per gateway, outcome and status class; omg_proxy_request_duration_ms_sum to divide by the count for a mean; and gauges for live gateways, pending gateways, dropped observations and which rate-limit backend is in use. It is unauthenticated and on the same port, so restrict it at the ingress if the deployment faces the internet. Counters are in-process: with several replicas each pod is a series and sum by (gateway) is the correct query.

Webhooks are delivered off the request path: three attempts with a short backoff, and an unsuccessful delivery is recorded as a failed row rather than retried forever. GET /api/gateways/<id>/webhooks/<hook_id>/deliveries is where "the hook is silent" gets answered — no matching event, or every POST failing. The monthly quota and the per-minute limit are different gates: the limiter charges a burst and lives in Redis when OMG_REDIS_URL is set; the quota is one row lock in Postgres, reserved before the call goes out, so two calls in a row cannot both read the same count. Both refuse with 429, and the row's reason says which one. Every response carries X-Request-Id — the caller's if it sent a sane one, otherwise one the guard minted — and the traffic row stores it, so a support ticket becomes one query.

O que é isto

OpenMCPGateway fica na frente de um ou mais servidores MCP. Os clientes apontam para https://<host>/g/<slug>/mcp; o gateway autentica quem chama, aplica seu portão e um orçamento por minuto, encaminha a requisição ao servidor real pela rede privada e registra o que aconteceu.

O upstream não precisa ser alcançável pela internet e não precisa saber quem é o chamador: o gateway encerra a identidade e encaminha sua própria credencial quando o upstream exige uma (upstream_token).

O painel responde às mesmas perguntas na mesma forma: a tela de Traffic traz totais com a variação contra a janela anterior, um gráfico de volume e quebras por desfecho, gateway e chamador — e uma linha em qualquer tabela abre um drawer com o resto daquela linha em vez de navegar para fora da lista.

Gateways

Um gateway é um slug, uma URL de upstream e uma política. O slug é global: /g/<slug>/mcp é a string que as pessoas colam nos clientes, então dois tenants não podem ambos ser donos de rancher.

Um gateway é criado para você: console, apontando para o MCP somente leitura desta própria implantação. O slug é global porque /g/<slug>/mcp é uma URL pública, então em uma implantação com vários tenants o primeiro fica com console e os outros com console-<tenant id> — o id, não um contador, para que o endereço ainda diga de quem é o gateway.

target_url é o endpoint streamable-HTTP do upstream, incluindo seu caminho (http://rancher-mcp.support.svc.cluster.local:8000/mcp). Precisa ser http:// ou https://.

Um gateway também decide quais ferramentas expõe. A lista é um conjunto de nomes de ferramentas do upstream; vazia significa tudo o que o upstream serve, que é como todo gateway começa. Ela pode ser estreitada por origem de credencial — o provedor de login (google, github, oidc), o rótulo de um verificador extra ou api_key — então uma rota dá a um bot um catálogo menor que o da pessoa logada ao lado, sem publicar dois gateways para o mesmo upstream. Uma origem sem lista própria herda a do gateway, e limpar a lista de uma origem a devolve a herdar. Uma ferramenta fora da lista desaparece de tools/list e um tools/call para ela responde 403 nomeando a ferramenta, então um cliente que manteve um nome antigo na config recebe uma frase em vez de um sucesso silencioso ou de uma caça a erro de digitação. A página do gateway sonda o upstream sob demanda: handshake de verdade, quantas ferramentas ele serve e o motivo da falha. Um upstream morto antes parecia um gateway silencioso e saudável.

O painel lê o catálogo do upstream diretamente para preencher essa lista - não pelo gateway, que responderia com o filtro que já está aplicando. Um nome configurado que o upstream não serve mais continua visível e marcado, porque sumir com ele em silêncio no próximo salvamento apagaria uma decisão do operador.

none - sem autenticação. Aceitável em rede privada; o painel avisa enquanto qualquer gateway assim estiver habilitado.

api_key - o chamador envia Authorization: Bearer omg_.... A chave é guardada como hash SHA-256 (é o que a autenticação compara) ao lado de uma cópia selada da plaintext, cifrada com o segredo da implantação. A resposta que a emite devolve a plaintext, e a página do gateway mostra um ícone de olho para chave que nunca foi lida: clicar decifra a cópia selada, mostra a chave uma vez e a apaga. Depois disso só resta o hash, e o único caminho de volta a uma chave legível é rotacioná-la. Uma chave pode ser emitida com validade. Depois dela a chave não autentica mais, e uma rotação herda o prazo da chave que substitui — o objetivo de rotacionar é trocar o segredo, não estender por quanto tempo ele é confiável.

O operador aprova uma vez, e essa conta passa a ser membro a partir daí.

O cliente não precisa de um token versionado em dotfile para o modo OAuth - essa é a ideia. Para o modo API-key precisa, e é por isso que a chave é por gateway e revogável isoladamente.

Um gateway também pode ter mais de uma forma de entrar. O modo oauth aceita chaves de API na mesma rota quando allow_api_key está ligado, e aceita tokens de emissores adicionais listados em verifiers - cada um com rótulo, emissor, audience opcional e URL do JWKS. Os emissores extras não têm fluxo de login próprio: o cliente já tem o token do seu provedor, e o gateway apenas confere assinatura, emissor e audience. Uma URL, um portão, um limite, e nenhum segundo gateway por tipo de credencial.

Quem pode chamar não é uma lista no gateway. Quem chama entra quando a conta pertence ao tenant dono do gateway - a mesma regra que o painel aplica para editá-lo, então "quem pode usar" tem uma resposta só, não duas que divergem. A associação é lida a cada requisição, então remover alguém ou desativar a conta fecha a porta do gateway na próxima chamada. Chaves de API são isentas porque a chave embute o próprio id em vez de nomear uma conta: uma chave entra enquanto o hash casar com uma chave viva aqui, e sai revogando a chave.

Membros e funções

Tudo é escopado a um tenant: gateways, membros, funções, tráfego, o log de auditoria. Um id de outro tenant é 404, não um 403 que confirma que ele existe.

As permissões são um catálogo fechado. Um erro de digitação é recusado com 422 nomeando o campo, porque a alternativa é uma função que não concede nada e não diz nada.

keys:read / writeVer ids de chaves e emitir, rotacionar ou revogar chaves

Duas funções são embutidas e não podem ser editadas nem excluídas, porque nenhuma das duas é uma decisão de política:

Um membro adicionado sem função cai em viewer: uma omissão estreita o acesso, nunca o amplia. A delegação também só pode estreitar - ninguém pode conceder uma permissão que não possui, ou members:write seria um caminho para role_owner. A mesma regra vale para o arquivo de configuração.

As permissões são resolvidas a cada requisição a partir dos read models, então editar uma função ou reatribuir alguém tem efeito no próximo clique. Sem novo login, sem sessão obsoleta.

Configuração como código

O painel e um arquivo YAML são duas portas de entrada para o mesmo command handler. Nenhum é privilegiado: um gateway criado no navegador é exportado para o arquivo, e um arquivo aplicado pela CI chega ao mesmo log de eventos que um clique.

gateways, roles e members são todos declarados no arquivo, então um tenant pode ser reconstruído a partir de um commit. Segredos nunca são exportados - escreva ${ENV_VAR} e o servidor resolve a partir do próprio ambiente no momento do apply.

# gateways.yaml
gateways:
  - slug: rancher
    name: Rancher cluster
    target_url: http://rancher-mcp.support.svc.cluster.local:8000/mcp
    description: read the cluster, restart and scale
    auth:
      mode: oauth
      idp: google
      client_id: ${GOOGLE_CLIENT_ID}
      client_secret: ${GOOGLE_CLIENT_SECRET}
      upstream_token: ${RANCHER_MCP_TOKEN}
    rate_limit: 120
    allow: [someone@example.com]

roles:
  - name: Auditor
    permissions: [gateways:read, traffic:read, audit:read]

members:
  - email: auditor@example.com
    password: ${MEMBER_PASSWORD}
    roles: [Auditor]

prune: false

Semântica de merge: o arquivo é autoritativo para o que declara. Um gateway omitido do arquivo sobrevive, então um erro de digitação não pode apagar produção. prune: true opta pela exclusão - vale apenas para gateways; membros nunca são removidos por omissão, porque uma conta que desaparece de um arquivo é muito mais provavelmente um acidente de merge do que uma intenção.

Membros reconciliam por email: um membro existente cujas funções diferem tem as funções substituídas, e um cujas funções coincidem é deixado como está. password só é usado quando a conta ainda não existe, então aparece em um arquivo revisado como ${MEMBER_PASSWORD} e nunca em uma exportação - o que também explica por que exportar e reaplicar é um no-op. Uma conta nova sem senha é recusada, porque inventar uma seria uma credencial com a qual ninguém consegue entrar.

Uma função cujo nome coincide com uma embutida (owner, viewer) pode ser nomeada mas não redefinida: caso contrário, o arquivo estreitaria todos os membros existentes de uma vez.

# round-trip from the shell
omg export --tenant tn_local > gateways.yaml
omg apply gateways.yaml --tenant tn_local

omg apply imprime o que mudou e quaisquer erros, e sai com código não zero quando uma declaração falhou - o que o torna utilizável na CI. API keys recém-emitidas são impressas uma vez, porque é a única vez em que o texto claro existe.

A página Config as code do painel faz o mesmo: Validate analisa e resolve placeholders sem tocar no estado, Apply executa os comandos.

API HTTP

Tudo o que o painel faz é um endpoint sob /api, autenticado por um cookie de sessão HttpOnly. As rotas MCP em si ficam em /g/<slug>/mcp e falam JSON-RPC, não esta API.

Toda lista é paginada por cursor: ?limit=50&before=<cursor>, respondendo {items, next}. next é null na última página, e limit é limitado a 200 em vez de recusado.

Cada lista também aceita seus próprios campos de filtro como parâmetros de query, uma caixa por coluna no painel. Colunas de texto casam um fragmento (?name=anch encontra rancher), status e enabled casam exatamente, e toda lista carrega uma caixa id para a linha que você copiou pela metade. Um campo desconhecido é 422 nomeando os campos que existem — um filtro silenciosamente ignorado é pior que um erro.

A ordenação é ?sort=<column>&order=asc|desc. As colunas ordenáveis são um conjunto fechado por lista: gateways por created_at, updated_at, name ou slug; traffic por occurred_at, duration_ms, status ou subject; o log de auditoria por occurred_at, actor ou type; membros por email e created_at; funções por name e created_at. Uma chave desconhecida é 422 que lista as válidas.

Um cursor significa depois desta linha, nesta ordem, então fica vinculado à ordenação sob a qual foi emitido. Mude sort ou order e comece da primeira página: reutilizar o cursor antigo é 422, não uma lista silenciosamente furada.

Dois endpoints não cabem na forma CRUD e vale conhecê-los: POST /api/gateways/<id>/keys/<key_id>/reveal devolve a plaintext selada uma vez e 409 depois disso, e GET /api/gateways/<id>/upstream-tools pergunta ao upstream o que ele serve para a lista ser marcada em vez de digitada. PUT /api/gateways/<id>/tools substitui a lista, ou a lista de uma origem de credencial quando o corpo nomeia um source. GET /api/requests.csv responde aos mesmos filtros de /requests, em arquivo; POST /api/config/plan diz o que um apply mudaria sem mudar nada, e POST /api/gateways/<id>/test sonda o upstream com um handshake MCP de verdade.

Quatro endpoints respondem a perguntas que a forma CRUD não responde: GET /api/gateways/<id>/history é o fluxo de eventos daquele gateway, do mais novo ao mais antigo, paginado e filtrado com o vocabulário do log de auditoria e com valores secretos ocultados; POST /api/gateways/<id>/restore reaplica a configuração de uma versão e anexa um fato gateway.restored — credenciais e chaves não são restauradas, porque uma chave revogada tem de continuar revogada; GET /api/events.csv é o log de auditoria como arquivo, com os mesmos filtros e o mesmo escopo de tenant; e /api/gateways/<id>/webhooks registra uma URL que recebe toda observação que o guard grava, assinada com um HMAC-SHA256 do corpo.

O console MCP

O gateway expõe um servidor MCP somente leitura próprio em /mcp, para que um agente possa responder perguntas sobre esta implantação: quais gateways existem, o que falhou na última hora, o que o log de auditoria diz sobre uma mudança de função.

É somente leitura por construção - toda ferramenta é uma consulta, nenhuma é um comando - e é escopado por tenant: um token emitido pelo operador de um tenant só consegue ler as linhas daquele tenant.

Todo tenant novo já tem um gateway apontando para ele. É criado junto com o tenant, chamado console, com o /mcp da própria implantação como upstream e uma API key para o chamador — então a primeira coisa que um tenant novo pode fazer é plugar um agente sem configurar nada. É um gateway como qualquer outro: mesma autenticação, mesmo rate limit, e suas perguntas caem no log de tráfego ao lado de qualquer outra chamada.

Tenants que existiam antes deste recurso recebem o mesmo gateway no próximo boot: o backfill busca tenants sem linha de gateway apontando para /mcp, então um owner que apagou o seu continua com ele apagado.

Conecte-se a ele exatamente como a um gateway feito à mão:

Operando

Os logs são um objeto JSON por linha em stdout, feitos para Loki / Grafana. Campos úteis para montar dashboards: event, gateway, subject, outcome, status, duration_ms. Defina o nível com OMG_LOG_LEVEL.

{"ts":"2026-11-02T11:04:14.538Z","level":"info","logger":"gateway","msg":"proxy.request","event":"proxy.request","gateway":"rancher","subject":"api-key:key_ab12","outcome":"allowed","status":200,"duration_ms":18,"ip":"203.0.113.7"}

O rate limiting é uma janela deslizante por (gateway, chamador). Com OMG_REDIS_URL setado, os contadores vivem no Redis e todas as réplicas os compartilham, então replicas: 2 significa o limite configurado e não o dobro dele. Sem isso o limiter é em processo: correto para uma réplica, N vezes o limite em N. Um Redis fora do ar falha aberto e loga - uma janela de contagem perdida é melhor que uma queda.

O estado do proxy OAuth (registros de clientes, tokens de upstream, mapeamentos de jti) vive no mesmo Postgres, cifrado em repouso, então um rollout não desconecta todos os clientes conectados. Essa parte já é segura para réplicas, e com OMG_REDIS_URL setado o limiter também é.

O estado é event-sourced. Toda mudança é um evento append-only e os read models são projeções dele, o que torna o log de auditoria confiável e permite que duas réplicas compartilhem um banco sem uma história de coerência de cache.

O schema é versionado em código (infrastructure/db/migrations.py): uma lista numerada de passos, registrada em schema_migrations. O boot aplica o que esta build ainda não aplicou, então uma atualização é um rollout, não uma sessão manual de psql. Os read models moram no próprio schema, readmodels — toda tabela com prefixo rm_ — enquanto events, as tabelas de unicidade e o histórico ficam em public. A divisão é o ponto: uma projeção é reconstruível a partir do log, então DROP SCHEMA readmodels CASCADE seguido de um boot é um reset seguro que o boot seguinte percebe e refaz. Nada de que o log depende está lá. OMG_RETENTION_DAYS poda o log de requisições no boot. Além do corte, eventos request.observed, rm_requests_tail e rm_request_stats são apagados; eventos de auditoria nunca, porque o log de quem mudou o quê não é o log de quem chamou. 0, o padrão, guarda tudo.

GET /metrics serve o formato texto do Prometheus: omg_proxy_requests_total por gateway, desfecho e classe de status; omg_proxy_request_duration_ms_sum para dividir pela contagem e obter uma média; e gauges para gateways no ar, gateways pendentes, observações descartadas e qual backend de rate limit está em uso. É sem autenticação e na mesma porta, então restrinja no ingress se a implantação estiver exposta à internet. Os contadores são em processo: com várias réplicas cada pod é uma série e sum by (gateway) é a consulta correta.

Webhooks são entregues fora do caminho da requisição: três tentativas com backoff curto, e uma entrega malsucedida vira uma linha failed em vez de retentar para sempre. GET /api/gateways/<id>/webhooks/<hook_id>/deliveries é onde "o hook está silencioso" ganha resposta — nenhum evento correspondente, ou todo POST falhando. A cota mensal e o limite por minuto são portões diferentes: o limitador cobra uma rajada e vive no Redis quando OMG_REDIS_URL está definido; a cota é um lock de linha no Postgres, reservado antes de a chamada sair, então duas chamadas seguidas não leem a mesma contagem. Ambos recusam com 429, e o reason da linha diz qual. Toda resposta carrega X-Request-Id — o do chamador, se veio um sensato, senão um que o guard gerou — e a linha de tráfego guarda esse id, então um chamado de suporte vira uma consulta.

Qué es esto

OpenMCPGateway se sitúa delante de uno o varios servidores MCP. Los clientes apuntan a https://<host>/g/<slug>/mcp; el gateway autentica al llamante, aplica su puerta y un presupuesto por minuto, reenvía la petición al servidor real por la red privada y registra lo que ha ocurrido.

El upstream no necesita ser accesible desde internet, y no necesita saber quién es el llamante: el gateway termina la identidad y reenvía su propia credencial cuando el upstream exige una (upstream_token).

El panel responde las mismas preguntas con la misma forma: la pantalla Traffic lleva totales con la variación respecto a la ventana anterior, un gráfico de volumen y desgloses por resultado, gateway y llamante — y una fila de cualquier tabla abre un cajón con el resto de esa fila en lugar de navegar fuera de la lista.

Gateways

Un gateway es un slug, una URL de upstream y una política. El slug es global: /g/<slug>/mcp es la cadena que la gente pega en los clientes, así que dos tenants no pueden poseer ambos rancher.

Hay un gateway creado por usted: console, apuntando al MCP de solo lectura de este propio despliegue. El slug es global porque /g/<slug>/mcp es una URL pública, así que en un despliegue con varios tenants el primero toma console y los demás toman console-<tenant id> — el id, no un contador, para que la dirección siga diciendo de quién es el gateway.

target_url es el endpoint streamable-HTTP del upstream, incluida su ruta (http://rancher-mcp.support.svc.cluster.local:8000/mcp). Debe ser http:// o https://.

Un gateway también decide qué herramientas expone. La lista es un conjunto de nombres de herramientas del upstream; vacía significa todo lo que sirve el upstream, que es como empieza todo gateway. Puede acotarse por origen de credencial — el proveedor de login (google, github, oidc), la etiqueta de un verificador extra o api_key — así una ruta da a un bot un catálogo menor que el de la persona conectada al lado, sin publicar dos gateways al mismo upstream. Una fuente sin lista propia hereda la del gateway, y limpiar la lista de una fuente la devuelve a heredar. Una herramienta fuera de la lista desaparece de tools/list y un tools/call hacia ella responde 403 nombrando la herramienta, así que un cliente que conservó un nombre viejo en su config recibe una frase en vez de un éxito silencioso o de una cacería de errata. La página del gateway sondea el upstream a demanda: handshake real, cuántas herramientas sirve y el motivo del fallo. Un upstream muerto antes parecía un gateway silencioso y sano.

El panel lee el catálogo del upstream directamente para llenar esa lista - no a través del gateway, que respondería con el filtro que ya aplica. Un nombre configurado que el upstream ya no sirve sigue visible y marcado, porque quitarlo en silencio en el siguiente guardado borraría una decisión del operador.

Modos de autenticación

none - sin autenticación. Correcto en una red privada; el panel avisa mientras haya habilitado un gateway así.

api_key - el llamador envía Authorization: Bearer omg_.... La clave se guarda como hash SHA-256 (eso es lo que compara la autenticación) junto a una copia sellada del texto plano, cifrada con el secreto del despliegue. La respuesta que la emite devuelve el texto plano, y la página del gateway muestra un icono de ojo para una clave que nunca se leyó: al pulsarlo se descifra la copia sellada, se muestra la clave una vez y se borra. Después de eso solo queda el hash, y el único camino de vuelta a una clave legible es rotarla. Una clave puede emitirse con caducidad. Pasada esa fecha la clave ya no autentica, y una rotación hereda el plazo de la clave que sustituye: rotar cambia el secreto, no cuánto tiempo se confía en él.

El operador aprueba una vez, y esa cuenta pasa a ser miembro desde entonces.

El cliente no necesita un token metido en un dotfile para el modo OAuth — de eso se trata. Para el modo API-key sí lo necesita, y por eso la clave es por gateway y revocable por sí sola.

Un gateway también puede tener más de una forma de entrar. El modo oauth acepta claves de API en la misma ruta cuando allow_api_key está activo, y acepta tokens de emisores adicionales listados en verifiers - cada uno con etiqueta, emisor, audience opcional y URL del JWKS. Los emisores extra no tienen flujo de inicio de sesión propio: el cliente ya tiene el token de su proveedor y el gateway solo comprueba firma, emisor y audience. Una URL, una puerta, un límite, y ningún segundo gateway por tipo de credencial.

Quién puede llamar no es una lista en el gateway. El llamante entra cuando su cuenta pertenece al tenant dueño del gateway — la misma regla que el panel aplica para editarlo, así que "quién puede usarlo" tiene una sola respuesta en vez de dos que se separan. La pertenencia se lee en cada petición, así que quitar a alguien o desactivar su cuenta cierra la puerta del gateway en su siguiente llamada. Las claves de API están exentas porque la clave incluye su propio id en lugar de nombrar una cuenta: una clave entra mientras su hash coincida con una clave viva aquí, y se revoca revocando la clave.

Miembros y roles

Todo está acotado a un tenant: gateways, miembros, roles, tráfico, el registro de auditoría. Un id de otro tenant es un 404, no un 403 que confirma que existe.

Los permisos son un catálogo cerrado. Una errata se rechaza con un 422 que nombra el campo, porque la alternativa es un rol que no concede nada y no dice nada.

Configuración como código

El panel y un archivo YAML son dos puertas de entrada al mismo manejador de comandos. Ninguno es privilegiado: un gateway creado en el navegador se exporta al archivo, y un archivo aplicado por CI llega al mismo registro de eventos que un clic.

gateways, roles y members se declaran todos en el archivo, así que un tenant se puede reconstruir desde un commit. Los secretos nunca se exportan — escriba ${ENV_VAR} y el servidor lo resuelve desde su propio entorno en el momento de aplicar.

# gateways.yaml
gateways:
  - slug: rancher
    name: Rancher cluster
    target_url: http://rancher-mcp.support.svc.cluster.local:8000/mcp
    description: read the cluster, restart and scale
    auth:
      mode: oauth
      idp: google
      client_id: ${GOOGLE_CLIENT_ID}
      client_secret: ${GOOGLE_CLIENT_SECRET}
      upstream_token: ${RANCHER_MCP_TOKEN}
    rate_limit: 120
    allow: [someone@example.com]

roles:
  - name: Auditor
    permissions: [gateways:read, traffic:read, audit:read]

members:
  - email: auditor@example.com
    password: ${MEMBER_PASSWORD}
    roles: [Auditor]

prune: false

Semántica de fusión: el archivo es autoritativo sobre lo que declara. Un gateway omitido del archivo sobrevive, así que una errata no puede borrar producción. prune: true opta por el borrado — se aplica solo a gateways; los miembros nunca se purgan por omisión, porque una cuenta que desaparece de un archivo es mucho más probable que sea un accidente de fusión que una intención.

Los miembros se reconcilian por email: a un miembro existente cuyos roles difieren se le reemplazan, y al que coincide se le deja igual. password solo se usa cuando la cuenta aún no existe, así que aparece en un archivo revisado como ${MEMBER_PASSWORD} y nunca en una exportación — que es también por qué exportar y volver a aplicar es una no-op. Una cuenta nueva sin contraseña se rechaza, porque inventarla sería una credencial con la que nadie puede iniciar sesión.

Un rol cuyo nombre coincide con uno integrado (owner, viewer) puede nombrarse pero no redefinirse: de lo contrario el archivo estrecharía a todos los miembros existentes a la vez.

# round-trip from the shell
omg export --tenant tn_local > gateways.yaml
omg apply gateways.yaml --tenant tn_local

omg apply imprime lo que cambió y cualquier error, y sale con código distinto de cero cuando una declaración falló — que es lo que lo hace usable en CI. Las claves de API recién emitidas se imprimen una vez, porque es la única vez que existe el texto plano.

La página Config as code del panel hace lo mismo: Validate analiza y resuelve los marcadores de posición sin tocar el estado, Apply ejecuta los comandos.

API HTTP

Todo lo que hace el panel es un endpoint bajo /api, autenticado por una cookie de sesión HttpOnly. Las rutas MCP viven en /g/<slug>/mcp y hablan JSON-RPC, no esta API.

Cada lista está paginada por cursor: ?limit=50&before=<cursor>, y responde {items, next}. next es null en la última página, y limit se recorta a 200 en lugar de rechazarse.

Cada lista acepta además sus propios campos de filtro como parámetros de consulta, una caja por columna en el panel. Las columnas de texto coinciden por fragmento (?name=anch encuentra rancher), status y enabled coinciden exactamente, y cada lista lleva una caja id para la fila que copió a medias. Un campo desconocido es un 422 que nombra los campos que existen — un filtro ignorado en silencio es peor que un error.

El orden es ?sort=<column>&order=asc|desc. Las columnas ordenables son un conjunto cerrado por lista: gateways por created_at, updated_at, name o slug; traffic por occurred_at, duration_ms, status o subject; el registro de auditoría por occurred_at, actor o type; members por email y created_at; roles por name y created_at. Una clave desconocida es un 422 que enumera las legales.

Un cursor significa después de esta fila, en este orden, así que está ligado al orden con el que se emitió. Cambie sort u order y empiece por la primera página: reutilizar el cursor antiguo es un 422, no una lista con agujeros silenciosos.

Dos endpoints no encajan en la forma CRUD y vale la pena conocerlos: POST /api/gateways/<id>/keys/<key_id>/reveal devuelve el texto plano sellado una vez y 409 después, y GET /api/gateways/<id>/upstream-tools pregunta al upstream qué sirve para que la lista se marque en vez de escribirse. PUT /api/gateways/<id>/tools reemplaza la lista, o la de un origen de credencial cuando el cuerpo nombra un source. GET /api/requests.csv responde a los mismos filtros de /requests, como archivo; POST /api/config/plan dice qué cambiaría un apply sin cambiar nada, y POST /api/gateways/<id>/test sondea el upstream con un handshake MCP real.

Cuatro endpoints responden preguntas que la forma CRUD no responde: GET /api/gateways/<id>/history es el flujo de eventos de ese gateway, del más nuevo al más antiguo, paginado y filtrado con el vocabulario del registro de auditoría y con los valores secretos ocultos; POST /api/gateways/<id>/restore reaplica la configuración de una versión y anexa un hecho gateway.restored — las credenciales y las claves no se restauran, porque una clave revocada debe seguir revocada; GET /api/events.csv es el registro de auditoría como archivo, con los mismos filtros y el mismo alcance de tenant; y /api/gateways/<id>/webhooks registra una URL que recibe cada observación que graba el guard, firmada con un HMAC-SHA256 del cuerpo.

El MCP de consola

El gateway expone un servidor MCP de solo lectura propio en /mcp, para que un agente pueda responder preguntas sobre este despliegue: qué gateways existen, qué falló en la última hora, qué dice el registro de auditoría sobre un cambio de rol.

Es de solo lectura por construcción — cada herramienta es una consulta, ninguna es un comando — y está acotado al tenant: un token emitido por el operador de un tenant solo puede leer las filas de ese tenant.

Todo tenant nuevo ya tiene un gateway apuntando a él. Se crea con el tenant, llamado console, con el /mcp del propio despliegue como upstream y una clave de API para el llamante — así que lo primero que puede hacer un tenant nuevo es enchufar un agente sin configurar nada. Es un gateway como cualquier otro: misma autenticación, mismo límite de tasa, y sus preguntas llegan al registro de tráfico junto a cualquier otra llamada.

Los tenants que existían antes de esta función reciben el mismo gateway en el siguiente arranque: el backfill busca tenants sin ninguna fila de gateway que apunte a /mcp, así que un owner que borró el suyo lo mantiene borrado.

Operarlo

Los logs son un objeto JSON por línea en stdout, construidos para Loki / Grafana. Campos útiles sobre los que construir dashboards: event, gateway, subject, outcome, status, duration_ms. Fije el nivel con OMG_LOG_LEVEL.

{"ts":"2026-11-02T11:04:14.538Z","level":"info","logger":"gateway","msg":"proxy.request","event":"proxy.request","gateway":"rancher","subject":"api-key:key_ab12","outcome":"allowed","status":200,"duration_ms":18,"ip":"203.0.113.7"}

El rate limiting es una ventana deslizante por (gateway, llamador). Con OMG_REDIS_URL definido, los contadores viven en Redis y todas las réplicas los comparten, así que replicas: 2 significa el límite configurado y no el doble. Sin eso el limitador es en proceso: correcto para una réplica, N veces el límite en N. Un Redis caído falla abierto y lo registra - una ventana de conteo perdida es mejor que una caída.

El estado del proxy OAuth (registros de clientes, tokens de upstream, mapeos de jti) vive en el mismo Postgres, cifrado en reposo, así que un despliegue no desconecta a todos los clientes conectados. Esa parte ya es segura entre réplicas, y con OMG_REDIS_URL definido el limitador también lo es.

El estado está basado en eventos. Cada cambio es un evento de solo adición y los read models son proyecciones de él, que es lo que hace fiable el registro de auditoría y permite que dos réplicas compartan una base de datos sin una historia de coherencia de caché.

El esquema está versionado en código (infrastructure/db/migrations.py): una lista numerada de pasos, registrada en schema_migrations. El arranque aplica lo que esta build aún no ha aplicado, así que una actualización es un despliegue, no una sesión manual de psql. Los read models viven en su propio esquema, readmodels — toda tabla con prefijo rm_ — mientras que events, las tablas de unicidad y el historial se quedan en public. La división es el punto: una proyección es reconstruible a partir del registro, así que DROP SCHEMA readmodels CASCADE seguido de un arranque es un reinicio seguro que el siguiente arranque detecta y repara. Nada de lo que el registro necesita está ahí. OMG_RETENTION_DAYS poda el log de peticiones al arrancar. Más allá del corte se borran los eventos request.observed, rm_requests_tail y rm_request_stats; los eventos de auditoría nunca, porque el log de quién cambió qué no es el log de quién llamó. 0, el valor por defecto, lo guarda todo.

GET /metrics sirve el formato de texto de Prometheus: omg_proxy_requests_total por gateway, desenlace y clase de estado; omg_proxy_request_duration_ms_sum para dividir por el conteo y sacar una media; y gauges para gateways en servicio, gateways pendientes, observaciones descartadas y qué backend de rate limit está en uso. No pide autenticación y va en el mismo puerto, así que restríngelo en el ingress si el despliegue mira a internet. Los contadores son en proceso: con varias réplicas cada pod es una serie y sum by (gateway) es la consulta correcta.

Los webhooks se entregan fuera del camino de la petición: tres intentos con un backoff corto, y una entrega fallida queda como fila failed en vez de reintentarse para siempre. GET /api/gateways/<id>/webhooks/<hook_id>/deliveries es donde "el hook está en silencio" obtiene respuesta — ningún evento coincidente, o todos los POST fallando. La cuota mensual y el límite por minuto son puertas distintas: el limitador cobra una ráfaga y vive en Redis cuando OMG_REDIS_URL está definido; la cuota es un bloqueo de fila en Postgres, reservado antes de que salga la llamada, así que dos llamadas seguidas no leen el mismo conteo. Ambos rechazan con 429, y el reason de la fila dice cuál. Cada respuesta lleva X-Request-Id — el del llamador, si envió uno sensato, si no uno que generó el guard — y la fila de tráfico guarda ese id, así que un ticket de soporte se convierte en una consulta.

这是什么

OpenMCPGateway 位于一个或多个 MCP 服务器之前。客户端指向 https://<host>/g/<slug>/mcp；网关认证调用方，应用它的准入判断和每分钟预算，通过私有网络将请求转发给真实服务器，并记录发生的情况。

上游不需要能从互联网访问，也不需要知道调用方是谁：网关负责终止身份，并在上游要求凭据时代为转发自己的凭据（upstream_token）。

面板以相同的形状回答同样的问题：Traffic 界面给出总量及与上一窗口的对比、一张流量图，以及按结果、网关和调用方的细分——任意表格中的一行都会打开抽屉显示该行的其余内容，而不是离开列表。

层行为
认证每个网关的 OAuth 代理（Google、GitHub、Microsoft、Discord、自定义 OIDC），或使用 SHA-256 哈希的 bearer 密钥
授权拥有该网关的租户成员。在此签发的密钥同样可用。

网关

网关是一个 slug、一个上游 URL 和一套策略。slug 是全局的：/g/<slug>/mcp 是人们粘贴到客户端里的字符串，因此两个租户不能同时拥有 rancher。

系统为你创建一个网关：console，指向本部署自己的只读 MCP。slug 是全局的，因为 /g/<slug>/mcp 是公开 URL，所以在有多个租户的部署上，第一个租户占用 console，其余租户使用 console-<tenant id>——用 id 而非计数器，这样地址仍然表明它是谁的网关。

target_url 是上游的 streamable-HTTP 端点，包含其路径（http://rancher-mcp.support.svc.cluster.local:8000/mcp）。必须是 http:// 或 https://。

网关还决定它暴露*哪些*工具。清单是一组上游工具名；为空表示上游提供的全部工具，这也是每个网关的初始状态。它可以按凭据来源收窄——托管的登录提供方（google、github、oidc）、额外验证器的标签，或 api_key——于是一条路由可以让机器人拿到的清单比旁边登录的人更小，不必为同一个上游发布两个网关。没有自己清单的来源继承网关的清单，清空某个来源的清单则让它重新继承。清单之外的工具会从 tools/list 消失，对它的 tools/call 会返回 403 并点名该工具，因此配置里还留着旧名字的客户端得到的是一句话，而不是静默成功或去猜拼写错在哪。网关页面可以按需探测上游：真实 handshake、可用的工具数量和失败原因。以前上游已死看起来只是网关安静而健康。

面板直接向上游读取目录来填充这份清单 - 不走网关，因为网关会用自己正在施加的过滤器来回答。上游已不再提供的已配置名字仍然可见并带标记，因为下次保存时静默删掉它会抹去操作者做过的决定。

字段含义
slug[a-z0-9-]+，2-40 个字符。出现在公开路径中
target_url上游 MCP 端点，包含路径
auth_modenone、api_key 或 oauth

认证方式

none - 无认证。在私有网络上没问题；只要有任何此类网关启用，面板就会警告。

api_key - 调用方发送 Authorization: Bearer omg_...。密钥以 SHA-256 哈希保存（鉴权比较的就是它），旁边是一份用部署密钥加密的明文封存副本。签发它的响应会返回明文，网关页面会给从未被读取过的密钥显示一个眼睛图标：点击会解密封存副本、把密钥显示一次，然后抹掉它。此后只剩哈希，想再拿到可读的密钥只能轮换。 密钥可以带有效期签发。过期后密钥不再通过认证，轮换会继承被替换密钥的期限——轮换是为了换密钥，而不是延长它被信任的时间。

操作员批准一次，该账号此后即为成员。

OAuth 模式下客户端不需要把令牌签入 dotfile——这正是重点。API 密钥模式则需如此，这也是密钥按网关划分、可单独吊销的原因。

一个网关也可以有多种进入方式。开启 allow_api_key 后，oauth 模式在同一路由上同时接受 API 密钥，并接受 verifiers 中列出的额外签发方的令牌——每项包含标签、签发方、可选 audience 和 JWKS 地址。这些额外签发方没有自己的登录流程：客户端已持有其提供方的令牌，网关只校验签名、签发方和 audience。一个 URL、同一道准入、同一个速率限制，无需按凭据类型拆分网关。

谁能调用不是网关上的一个名单。调用者的账号属于拥有该网关的租户时才放行——面板编辑网关用的也是同一条规则，于是「谁能使用」只有一个答案，而不是两个会逐渐分叉的答案。成员关系逐请求读取，因此移除某人或禁用其账号会在下一次调用时关闭网关的门。API 密钥不受此限，因为密钥内嵌自己的 id 而不是指向某个账号：密钥的哈希与本网关中有效密钥匹配即放行，撤销密钥即拒绝。

成员与角色

一切都以租户为范围：网关、成员、角色、流量、审计日志。来自其他租户的 id 返回 404，而不是会确认其存在的 403。

权限是一个封闭的目录。拼写错误会以 422 拒绝并指出字段名，因为另一种结果是一个不授予任何权限也不说明任何事的角色。

权限授予
gateways:read / write查看网关列表，并修改 slug、目标、认证和限制
keys:read / write查看密钥 id，并签发、轮换或吊销密钥
traffic:read读取请求统计和最近请求日志
audit:read读取仅追加的事件日志
config:read / write导出并应用 YAML 文件
members:read / write查看通讯录，并添加人员
roles:read / write查看角色表，并定义或编辑角色

有两个内置角色，无法编辑或删除，因为两者都不是策略决策：

角色Id权限
ownerrole_owner全部
viewerrole_viewer所有读取权限

未指定角色添加的成员会落到 viewer：遗漏只会收窄访问，绝不会放宽。委派也只能收窄——没有人能授予自己不拥有的权限，否则 members:write 就会成为通往 role_owner 的路径。同样的规则适用于配置文件。

权限在每次请求时从读模型解析，因此编辑角色或重新分配某人会在其下一次点击时生效。无需重新登录，没有过期会话。

配置即代码

面板和 YAML 文件是通向同一命令处理器的两扇前门。两者都没有特权：在浏览器中创建的网关会导出到文件，而由 CI 应用的文件与一次点击进入同一个事件日志。

gateways、roles 和 members 都在文件中声明，因此租户可以从一次提交重建。密钥永不导出——写下 ${ENV_VAR}，服务器在应用时从自己的环境解析它。

# gateways.yaml
gateways:
  - slug: rancher
    name: Rancher cluster
    target_url: http://rancher-mcp.support.svc.cluster.local:8000/mcp
    description: read the cluster, restart and scale
    auth:
      mode: oauth
      idp: google
      client_id: ${GOOGLE_CLIENT_ID}
      client_secret: ${GOOGLE_CLIENT_SECRET}
      upstream_token: ${RANCHER_MCP_TOKEN}
    rate_limit: 120
    allow: [someone@example.com]

roles:
  - name: Auditor
    permissions: [gateways:read, traffic:read, audit:read]

members:
  - email: auditor@example.com
    password: ${MEMBER_PASSWORD}
    roles: [Auditor]

prune: false

合并语义：文件对其声明的内容具有权威性。文件中省略的网关会保留，因此拼写错误无法删除生产环境。prune: true 选择启用删除——它仅适用于网关；成员绝不会因为省略而被清理，因为从文件中消失的账号更可能是合并事故而非有意为之。

成员按 email 对账：角色不同的现有成员会被替换角色，角色相同的则保持不变。password 仅在账号尚不存在时使用，因此它出现在经过审阅的文件中为 ${MEMBER_PASSWORD}，而绝不会出现在导出中——这也是导出再重新应用是空操作的原因。没有密码的新账号会被拒绝，因为凭空编造一个将是谁都无法登录的凭据。

名称与内置角色（owner、viewer）相同的角色可以被点名但不可重定义：否则文件会一次性收窄所有现有成员。

# round-trip from the shell
omg export --tenant tn_local > gateways.yaml
omg apply gateways.yaml --tenant tn_local

omg apply 打印变更内容和任何错误，并在某个声明失败时以非零退出——这正是它可用于 CI 的原因。新签发的 API 密钥只打印一次，因为那是明文唯一存在的时刻。

面板的 Config as code 页面做同样的事：Validate 解析并解析占位符而不触碰状态，Apply 执行命令。

HTTP API

面板所做的一切都是 /api 下的端点，由 HttpOnly 会话 cookie 认证。MCP 路由本身位于 /g/<slug>/mcp，使用 JSON-RPC，而不是这套 API。

每个列表都是游标分页：?limit=50&before=<cursor>，返回 {items, next}。next 在最后一页为 null，limit 会被钳制到 200 而不是被拒绝。

每个列表还接受自己的过滤字段作为查询参数，对应面板中每列一个输入框。文本列匹配片段（?name=anch 可找到 rancher），status 和 enabled 精确匹配，每个列表都带有一个 id 输入框，用于你只复制了一半的那一行。未知字段会返回 422 并列出存在的字段——被静默忽略的过滤比报错更糟。

排序是 ?sort=<column>&order=asc|desc。可排序列对每个列表是封闭集合：网关按 created_at、updated_at、name 或 slug；流量按 occurred_at、duration_ms、status 或 subject；审计日志按 occurred_at、actor 或 type；成员按 email 和 created_at；角色按 name 和 created_at。未知的键会返回 422 并列出合法的键。

游标意味着*在此行之后，按此顺序*，因此它绑定于签发它的排序。更改 sort 或 order 后请从第一页开始：复用旧游标会得到 422，而不是一个静默有洞的列表。

有两个端点不合 CRUD 的形状，值得了解：POST /api/gateways/<id>/keys/<key_id>/reveal 返回一次封存的明文，之后是 409；GET /api/gateways/<id>/upstream-tools 向上游询问它提供什么，好让清单被勾选而不是手打。PUT /api/gateways/<id>/tools 替换清单；请求体点名 source 时替换该来源的清单。 GET /api/requests.csv 以文件形式响应与 /requests 相同的筛选条件；POST /api/config/plan 说明 apply 会改什么而不改动任何东西；POST /api/gateways/<id>/test 用真实的 MCP handshake 探测上游。

有四个端点回答 CRUD 形状无法回答的问题：GET /api/gateways/<id>/history 是该网关自己的事件流，从新到旧，按审计日志的词汇分页和过滤，敏感值已脱敏；POST /api/gateways/<id>/restore 重新应用某个版本的配置，并追加一条 gateway.restored 事实——凭据和密钥不会被恢复，因为已撤销的密钥必须保持撤销；GET /api/events.csv 是以文件形式导出的审计日志，过滤条件和租户范围相同；/api/gateways/<id>/webhooks 注册一个 URL，接收 guard 记录的每一条观测，并用请求体的 HMAC-SHA256 签名。

console MCP

网关在 /mcp 暴露自己的只读 MCP 服务器，因此 agent 可以回答关于*本部署*的问题：存在哪些网关、过去一小时什么失败了、审计日志对某次角色变更说了什么。

它在构造上就是只读的——每个工具都是查询，没有一个是命令——并且以租户为范围：某个租户操作员签发的令牌只能读取该租户的行。

每个新租户都已经有一个指向它的网关。它随租户一起创建，名为 console，以上游为本部署自己的 /mcp，并为调用方准备一个 API 密钥——因此新租户要做的第一件事就是接入一个 agent，无需任何配置。它和其他网关一样：相同的认证、相同的速率限制，它的问题会和其他每次调用一样落在流量日志中。

在此功能之前存在的租户会在下次启动时获得相同的网关：回填会请求那些没有指向 /mcp 的网关行的租户，因此删除了自己网关的 owner 会保持删除状态。

运维

日志在 stdout 上每行一个 JSON 对象，为 Loki / Grafana 构建。可用于构建仪表盘的有用字段：event、gateway、subject、outcome、status、duration_ms。用 OMG_LOG_LEVEL 设置级别。

{"ts":"2026-11-02T11:04:14.538Z","level":"info","logger":"gateway","msg":"proxy.request","event":"proxy.request","gateway":"rancher","subject":"api-key:key_ab12","outcome":"allowed","status":200,"duration_ms":18,"ip":"203.0.113.7"}

限流是按（网关、调用方）的滑动窗口。设置 OMG_REDIS_URL 后，计数器放在 Redis 里、由所有副本共享，因此 replicas: 2 意味着配置的限额而不是它的两倍。不设置时限流器在进程内：单副本时正确，N 个副本时限额是 N 倍。Redis 挂掉时放行并记录 - 丢一个计数窗口好过一次故障。

OAuth 代理状态（客户端注册、上游令牌、jti 映射）存放在同一个 Postgres 里，静态加密，因此滚动发布不会把所有已连接的客户端踢下线。这部分本就是副本安全的；设置了 OMG_REDIS_URL 后限流器也是。

状态是事件溯源的。每次变更都是一个仅追加的事件，读模型是其投影，这正是审计日志可信的原因，也让两个副本共享一个数据库而无需缓存一致性方案。

schema 在代码中版本化（infrastructure/db/migrations.py）：一个编号的步骤列表，记录在 schema_migrations 中。启动时应用此构建尚未应用的所有内容，因此升级是一次滚动发布，而不是手动 psql 会话。读模型住在自己的 schema readmodels 里——所有以 rm_ 为前缀的表——而 events、唯一性表和版本历史留在 public。这个划分正是重点：投影可以从日志重建，因此 DROP SCHEMA readmodels CASCADE 再加一次启动是安全的重置，下一次启动会发现并修好它。日志依赖的任何东西都不在那里。 OMG_RETENTION_DAYS 在启动时清理请求日志。超过截止时间后，request.observed 事件、rm_requests_tail 和 rm_request_stats 会被删除；审计事件永不删除，因为“谁改了什么”的日志不是“谁调用了什么”的日志。默认值 0 表示全部保留。

GET /metrics 输出 Prometheus 文本格式：按网关、结果和状态类别统计的 omg_proxy_requests_total；除以计数得到均值的 omg_proxy_request_duration_ms_sum；以及在线网关、待定网关、被丢弃的观测和当前限流后端的 gauge。它不鉴权且在同一端口上，因此如果部署面向公网，请在 ingress 上限制它。计数器在进程内：多副本时每个 pod 是一条序列，sum by (gateway) 才是正确的查询。

Webhook 在请求路径之外投递：三次尝试、短暂退避，投递失败会写成一行 failed，而不是无限重试。GET /api/gateways/<id>/webhooks/<hook_id>/deliveries 回答"这个 hook 为什么没声了"——没有匹配的事件，还是每次 POST 都失败。月度配额和每分钟限制是两道不同的门：限流器计的是突发量，配置 OMG_REDIS_URL 时存在 Redis；配额是 Postgres 里的一次行锁，在调用发出前预留，所以连续两次调用不可能读到同一个计数。两者都用 429 拒绝，行里的 reason 说明是哪一道。每个响应都带 X-Request-Id——调用方给了合规的就用它，否则用 guard 生成的——流量行会存下它，于是一个工单就是一条查询。

症状通常是什么
网关路由返回 503没有客户端凭据的 OAuth 网关。按设计故障关闭
每次调用都返回 401上游令牌错误或未设置，或客户端的密钥已被轮换
带着主体返回 403调用者的账号不属于拥有该网关的租户

Что это такое

OpenMCPGateway стоит перед одним или несколькими серверами MCP. Клиенты обращаются к https://<host>/g/<slug>/mcp; шлюз аутентифицирует вызывающего, применяет свой шлюз доступа и лимит запросов в минуту, пересылает запрос на реальный сервер по приватной сети и записывает, что произошло.

Апстриму не нужно быть доступным из интернета, и ему не нужно знать, кто вызывает: шлюз завершает идентификацию и пересылает собственный credential, когда апстрим его требует (upstream_token).

Панель отвечает на те же вопросы в той же форме: экран Traffic несёт итоги с изменением относительно предыдущего окна, график объёма и разбивки по outcome, шлюзу и вызывающему — а строка в любой таблице открывает выдвижную панель с остальными полями этой строки вместо перехода со списка.

АвторизацияУчастники тенанта, которому принадлежит шлюз. Ключ, выпущенный здесь, тоже подходит.
Лимит частотыНа субъект, на шлюз, считаются JSON-RPC запросы. Handshake бесплатен

Быстрый старт

Нужны Postgres, доступный шлюзу, и хостнейм, завершающий TLS перед ним.

# 1. run it
export OMG_DATABASE_URL=postgresql://omg:omg@127.0.0.1:5432/omg
export OMG_SESSION_SECRET=$(openssl rand -hex 32)
export OMG_BASE_URL=https://gateway.example.com
omg serve

# 2. create the first account, then a tenant, in the browser
open https://gateway.example.com

Первый аккаунт создаёт тенант и становится его owner. Остальные либо присоединяются по join-коду тенанта, либо их добавляет администратор.

Тенант появляется с уже существующим шлюзом console, указывающим на собственный read-only MCP этого деплоймента. Направьте агента на /g/console/mcp с API-ключом со страницы шлюза и спросите, что делает деплоймент — апстрим настраивать не нужно.

Направьте клиента на шлюз, как только он появится:

// opencode.json
{
  "mcp": {
    "my-server": {
      "type": "remote",
      "url": "https://gateway.example.com/g/my-server/mcp"
    }
  }
}

Шлюзы

Шлюз — это slug, URL апстрима и политика. Slug глобальный: /g/<slug>/mcp — строка, которую люди вставляют в клиенты, поэтому два тенанта не могут оба владеть rancher.

Один шлюз создаётся за вас: console, указывающий на собственный read-only MCP этого деплоймента. Slug глобальный, потому что /g/<slug>/mcp — публичный URL, поэтому на деплойменте с несколькими тенантами первый забирает console, а остальные — console-<tenant id>: id, а не счётчик, чтобы адрес всё ещё говорил, чей это шлюз.

target_url — это streamable-HTTP endpoint апстрима, включая его путь (http://rancher-mcp.support.svc.cluster.local:8000/mcp). Он должен быть http:// или https://.

Шлюз решает и какие инструменты он отдаёт. Список - это набор имён инструментов upstream; пустой означает всё, что отдаёт upstream, и именно так начинается каждый шлюз. Его можно сузить по источнику учётных данных — размещённый провайдер входа (google, github, oidc), метка дополнительного верификатора или api_key — и тогда один маршрут даёт боту меньший каталог, чем человеку, вошедшему рядом, без публикации двух шлюзов на один upstream. Источник без своего списка наследует список шлюза, а очистка списка источника возвращает его к наследованию. Инструмент вне списка исчезает из tools/list, а tools/call к нему отвечает 403 с именем инструмента, так что клиент, сохранивший старое имя в конфиге, получает фразу вместо тихого успеха или поиска опечатки. Страница шлюза проверяет upstream по требованию: настоящее рукопожатие, число инструментов и причину сбоя. Мёртвый upstream раньше выглядел как тихий и здоровый шлюз.

Панель читает каталог upstream напрямую, чтобы заполнить этот список - не через шлюз, который ответил бы тем фильтром, который уже применяет. Настроенное имя, которое upstream больше не отдаёт, остаётся видимым и помеченным: тихо убрать его при следующем сохранении значило бы стереть решение оператора.

Режимы аутентификации

none — без аутентификации. Нормально в приватной сети; панель предупреждает, пока любой такой шлюз включён.

api_key - вызывающий присылает Authorization: Bearer omg_.... Ключ хранится как SHA-256-хеш (именно с ним сравнивает аутентификация) рядом с запечатанной копией открытого текста, зашифрованной секретом деплоймента. Ответ, который его выдаёт, возвращает открытый текст, а на странице шлюза у никогда не прочитанного ключа есть значок глаза: нажатие расшифровывает запечатанную копию, показывает ключ один раз и стирает её. После этого остаётся только хеш, и единственный путь к читаемому ключу - ротация. Ключ можно выпустить со сроком действия. После него ключ не аутентифицирует, а ротация наследует срок заменяемого ключа: смысл ротации — сменить секрет, а не продлить доверие к нему.

Оператор одобряет один раз, и эта учётная запись с этого момента становится участником.

Клиенту не нужен токен, вписанный в dotfile, для режима OAuth — в этом и смысл. Для режима API-ключа нужен, поэтому ключ привязан к шлюзу и отзывается отдельно.

У шлюза может быть несколько способов входа. В режиме oauth при включённом allow_api_key тот же маршрут принимает API-ключи, а в verifiers перечисляются дополнительные издатели - для каждого метка, издатель, необязательный audience и URL JWKS. У этих издателей нет своего входа: у клиента уже есть токен провайдера, а шлюз проверяет подпись, издателя и audience. Один URL, одни ворота, один лимит, и никаких отдельных шлюзов под каждый тип учётных данных.

Кто может вызывать — это не список на шлюзе. Вызывающий проходит, когда его учётная запись принадлежит тенанту, владеющему шлюзом: то же правило панель применяет к редактированию, поэтому у вопроса «кто может пользоваться» один ответ, а не два, которые расходятся. Членство читается на каждом запросе, поэтому удаление участника или отключение учётной записи закрывает дверь шлюза на следующем вызове. API-ключи исключены, потому что ключ содержит собственный id, а не имя учётной записи: ключ проходит, пока его хеш совпадает с живым ключом шлюза, и отзывается отзывом ключа.

# API-key call
curl -sS https://gateway.example.com/g/rancher/mcp \
  -H 'Authorization: Bearer omg_...' \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"0"}}}'

Участники и роли

Всё привязано к тенанту: шлюзы, участники, роли, трафик, аудит-лог. Id из другого тенанта — это 404, а не 403, подтверждающий, что он существует.

Разрешения — закрытый каталог. Опечатка отклоняется с 422, называющим поле, потому что альтернатива — роль, которая ничего не даёт и ничего не сообщает.

РазрешениеДаёт
gateways:read / writeВидеть список шлюзов и менять slug, таргеты, auth и лимиты
keys:read / writeВидеть id ключей и выпускать, ротировать или отзывать их
traffic:readЧитать статистику запросов и лог последних запросов
audit:readЧитать append-only лог событий
config:read / writeЭкспортировать и применять YAML-файл
members:read / writeВидеть адресную книгу и добавлять людей
roles:read / writeВидеть таблицу ролей и определять или редактировать роли

Две роли встроены, и их нельзя редактировать или удалять, поскольку ни одна не является политическим решением:

РольIdРазрешения
ownerrole_ownerвсё
viewerrole_viewerвсе read-разрешения

Участник, добавленный без роли, попадает в viewer: пропуск сужает доступ, но никогда не расширяет. Делегирование тоже может только сужать — никто не может выдать разрешение, которым сам не владеет, иначе members:write стал бы путём к role_owner. То же правило применяется к конфиг-файлу.

Разрешения вычисляются на каждый запрос из read-моделей, поэтому редактирование роли или переназначение кого-то вступает в силу при следующем клике. Без повторного входа, без устаревшей сессии.

Конфигурация как код

Панель и YAML-файл — две передние двери к одному и тому же обработчику команд. Ни одна не привилегирована: шлюз, созданный в браузере, экспортируется в файл, а файл, применённый из CI, попадает в тот же лог событий, что и клик.

gateways, roles и members объявляются в файле, поэтому тенант можно восстановить из коммита. Секреты никогда не экспортируются — напишите ${ENV_VAR}, и сервер разрешит её из своего окружения во время apply.

# gateways.yaml
gateways:
  - slug: rancher
    name: Rancher cluster
    target_url: http://rancher-mcp.support.svc.cluster.local:8000/mcp
    description: read the cluster, restart and scale
    auth:
      mode: oauth
      idp: google
      client_id: ${GOOGLE_CLIENT_ID}
      client_secret: ${GOOGLE_CLIENT_SECRET}
      upstream_token: ${RANCHER_MCP_TOKEN}
    rate_limit: 120
    allow: [someone@example.com]

roles:
  - name: Auditor
    permissions: [gateways:read, traffic:read, audit:read]

members:
  - email: auditor@example.com
    password: ${MEMBER_PASSWORD}
    roles: [Auditor]

prune: false

Семантика слияния: файл авторитетен для того, что он объявляет. Шлюз, отсутствующий в файле, выживает, поэтому опечатка не может удалить продакшн. prune: true включает удаление — оно применяется только к шлюзам; участники никогда не удаляются по пропуску, потому что аккаунт, исчезнувший из файла, гораздо вероятнее случай слияния, чем намерение.

Участники сверяются по email: существующему участнику с отличающимися ролями роли заменяются, а тот, чьи роли совпадают, остаётся нетронутым. password используется только когда аккаунта ещё нет, поэтому в проверяемом файле он выглядит как ${MEMBER_PASSWORD} и никогда в экспорте — поэтому же экспорт и повторный apply ничего не меняют. Новый аккаунт без пароля отклоняется, потому что придуманный пароль был бы credential, которым никто не может войти.

Роль, чьё имя совпадает со встроенной (owner, viewer), можно назвать, но не переопределить: иначе файл сузил бы сразу всех существующих участников.

# round-trip from the shell
omg export --tenant tn_local > gateways.yaml
omg apply gateways.yaml --tenant tn_local

omg apply печатает, что изменилось, и любые ошибки, и завершается с ненулевым кодом, когда объявление не удалось — именно это делает его пригодным для CI. Новые выпущенные API-ключи печатаются один раз, потому что это единственный момент, когда plaintext существует.

Страница Config as code в панели делает то же самое: Validate разбирает и разрешает плейсхолдеры, не трогая состояние, Apply выполняет команды.

HTTP API

Всё, что делает панель, — это endpoint под /api, аутентифицируемый HttpOnly session-cookie. Сами маршруты MCP живут на /g/<slug>/mcp и говорят JSON-RPC, а не на этом API.

Каждый список курсорно пагинирован: ?limit=50&before=<cursor>, отвечает {items, next}. next равен null на последней странице, а limit приводится к 200, а не отклоняется.

Каждый список также принимает свои поля-фильтры как query-параметры, по одному полю на колонку в панели. Текстовые колонки совпадают по фрагменту (?name=anch находит rancher), status и enabled совпадают точно, и каждый список несёт поле id для строки, которую вы скопировали только наполовину. Неизвестное поле — это 422, называющий существующие поля: молча проигнорированный фильтр хуже ошибки.

Сортировка — ?sort=<column>&order=asc|desc. Сортируемые колонки — закрытый набор для каждого списка: шлюзы по created_at, updated_at, name или slug; трафик по occurred_at, duration_ms, status или subject; аудит-лог по occurred_at, actor или type; участники по email и created_at; роли по name и created_at. Неизвестный ключ — это 422, перечисляющий допустимые.

Курсор означает после этой строки, в этом порядке, поэтому он привязан к сортировке, под которой был выпущен. Измените sort или order и начните с первой страницы: повторное использование старого курсора — это 422, а не молчаливо дырявый список.

Два эндпоинта не вписываются в форму CRUD, и о них стоит знать: POST /api/gateways/<id>/keys/<key_id>/reveal один раз возвращает запечатанный открытый текст, а дальше 409; GET /api/gateways/<id>/upstream-tools спрашивает upstream, что он отдаёт, чтобы список отмечали, а не печатали. PUT /api/gateways/<id>/tools заменяет список или список одного источника учётных данных, если в теле указан source. GET /api/requests.csv отвечает на те же фильтры, что /requests, файлом; POST /api/config/plan говорит, что изменит apply, ничего не меняя, а POST /api/gateways/<id>/test проверяет upstream настоящим MCP-рукопожатием.

Четыре эндпоинта отвечают на вопросы, которых нет в CRUD-форме: GET /api/gateways/<id>/history — собственный поток событий этого шлюза, от новых к старым, с постраничной выдачей, фильтрами журнала аудита и вырезанными секретами; POST /api/gateways/<id>/restore заново применяет конфигурацию версии и добавляет один факт gateway.restored — учётные данные и ключи не восстанавливаются, потому что отозванный ключ должен остаться отозванным; GET /api/events.csv — журнал аудита в виде файла с теми же фильтрами и той же областью арендатора; /api/gateways/<id>/webhooks регистрирует URL, получающий каждое наблюдение guard'а, подписанное HMAC-SHA256 тела.

Console MCP

Шлюз предоставляет собственный read-only MCP-сервер на /mcp, чтобы агент мог отвечать на вопросы об этом деплойменте: какие шлюзы существуют, что упало за последний час, что аудит-лог говорит об изменении роли.

Он read-only по построению — каждый инструмент это запрос, ни один не команда — и ограничен тенантом: токен, выпущенный оператором одного тенанта, может читать только строки этого тенанта.

У каждого нового тенанта уже есть один шлюз, указывающий на него. Он создаётся вместе с тенантом, называется console, его апстрим — собственный /mcp деплоймента, а для вызывающего выпускается API-ключ — так что первое, что может сделать новый тенант, — подключить агента, ничего не настраивая. Это шлюз как любой другой: та же auth, тот же лимит, и его вопросы попадают в лог трафика рядом со всеми остальными вызовами.

Тенанты, существовавшие до этой функции, получают тот же шлюз при следующей загрузке: backfill ищет тенантов без строки шлюза, указывающей на /mcp, поэтому владелец, удаливший свой, сохраняет его удалённым.

Подключайтесь к нему точно как к шлюзу, сделанному вручную:

// opencode.json
{
  "mcp": {
    "gateway-console": {
      "type": "remote",
      "url": "https://gateway.example.com/g/console/mcp",
      "headers": { "Authorization": "Bearer omgc_gateway_api_key" }
    }
  }
}

Ключ выпускается при создании тенанта и показывается один раз, на странице шлюза. Ротируйте его там, если он утёк; удалите шлюз, если предпочитаете вызывать /mcp напрямую.

1. Выпустите токен: POST /api/mcp/token с вашим session-cookie. Plaintext возвращается один раз, точно как API-ключ.

2. Направьте клиента на него:

// opencode.json
{
  "mcp": {
    "gateway-console": {
      "type": "remote",
      "url": "https://gateway.example.com/mcp",
      "headers": { "Authorization": "Bearer omg_..." }
    }
  }
}

3. Спрашивайте его: какие шлюзы сейчас падают, покажи последние 20 вызовов, ограниченных лимитом, для шлюза rancher, что изменилось в аудит-логе сегодня.

Токен подписан секретом деплоймента, несёт id оператора и время выпуска и истекает через 90 дней. Отзовите его, ротировав OMG_SESSION_SECRET — что также разлогинит всех, поэтому предпочтите короткий срок, если это важнее.

Эксплуатация

Логи — один JSON-объект на строку в stdout, собранный под Loki / Grafana. Полезные поля для дашбордов: event, gateway, subject, outcome, status, duration_ms. Уровень задаётся через OMG_LOG_LEVEL.

{"ts":"2026-11-02T11:04:14.538Z","level":"info","logger":"gateway","msg":"proxy.request","event":"proxy.request","gateway":"rancher","subject":"api-key:key_ab12","outcome":"allowed","status":200,"duration_ms":18,"ip":"203.0.113.7"}

Rate limiting - это скользящее окно на пару (шлюз, вызывающий). Если задан OMG_REDIS_URL, счётчики живут в Redis и общие для всех реплик, поэтому replicas: 2 означает настроенный лимит, а не двойной. Без него лимитер в процессе: верно для одной реплики, N лимитов при N. Упавший Redis пропускает и пишет в лог - потерянное окно учёта лучше простоя.

Состояние OAuth-прокси (регистрации клиентов, токены upstream, отображения jti) живёт в том же Postgres, зашифрованное при хранении, поэтому раскатка не разлогинивает всех подключённых клиентов. Эта часть уже безопасна для реплик, а с заданным OMG_REDIS_URL - и лимитер.

Состояние event-sourced. Каждое изменение — append-only событие, а read-модели — его проекции, что делает аудит-лог достоверным и позволяет двум репликам делить одну базу без истории согласованности кеша.

Схема версионируется в коде (infrastructure/db/migrations.py): нумерованный список шагов, записываемый в schema_migrations. Загрузка применяет всё, что эта сборка ещё не применила, поэтому обновление — это выкатка, а не ручная сессия psql. Read-модели живут в собственной схеме readmodels — все таблицы с префиксом rm_ — а events, таблицы уникальности и история остаются в public. В этом и смысл разделения: проекция перестраивается из лога, поэтому DROP SCHEMA readmodels CASCADE и последующая загрузка — безопасный сброс, который следующая загрузка замечает и чинит. Ничего, от чего зависит лог, там нет. OMG_RETENTION_DAYS чистит журнал запросов при старте. За границей срока удаляются события request.observed, rm_requests_tail и rm_request_stats; события аудита — никогда, потому что журнал «кто что изменил» не то же, что журнал «кто вызвал». 0 по умолчанию хранит всё.

GET /metrics отдаёт текстовый формат Prometheus: omg_proxy_requests_total по шлюзу, исходу и классу статуса; omg_proxy_request_duration_ms_sum, чтобы поделить на счётчик и получить среднее; и gauges для работающих шлюзов, ожидающих шлюзов, отброшенных наблюдений и того, какой бэкенд rate limit используется. Он без аутентификации и на том же порту, поэтому ограничьте его на ingress, если деплоймент смотрит в интернет. Счётчики в процессе: при нескольких репликах каждый pod - отдельная серия, и sum by (gateway) - правильный запрос.

Webhooks доставляются вне пути запроса: три попытки с короткой паузой, а неудачная доставка остаётся строкой failed, а не повторяется бесконечно. GET /api/gateways/<id>/webhooks/<hook_id>/deliveries — место, где у вопроса "почему хук молчит" появляется ответ: нет подходящего события или падают все POST. Месячная квота и лимит в минуту — разные ворота: лимитер считает всплеск и живёт в Redis, когда задан OMG_REDIS_URL; квота — это одна блокировка строки в Postgres, занятая до отправки вызова, поэтому два вызова подряд не могут прочитать один и тот же счётчик. Оба отказывают с 429, и reason в строке говорит, какой именно. Каждый ответ несёт X-Request-Id — вызывающего, если он прислал разумный, иначе сгенерированный guard'ом, — и строка трафика его хранит, так что обращение в поддержку превращается в один запрос.

Окружение

Настройка входа — это конфигурация деплоймента, а не тенанта: владелец одного тенанта не должен иметь возможности менять то, как входят все. Поэтому она берётся из окружения, и экрана для неё нет.
